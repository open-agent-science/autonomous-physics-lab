## How to read the verification tags

- CONFIRMED: an independent verifier reproduced the evidence and agreed
  with the severity.
- PARTIAL: the core claim held but a number or the scope was corrected;
  see the per-finding correction line.
- REFUTED: an independent verifier showed the evidence does not hold;
  the finding is kept for transparency but should NOT drive any fix.
- REAUDIT: produced by the fresh Opus re-audit of the security/CI
  dimension (the first pass returned only one finding for it).
- UNVERIFIED: the adversarial re-check did not complete; treat the
  finding as auditor-reported but not independently confirmed. (None
  remain in the final memo.)

## Core package architecture (physics_lab/)

The physics_lab package (178 files, ~48k LOC) has drifted far from its documented architecture: AGENTS.md (lines 373-387) still describes a 10-module lab (cli, 5 engines, 4 registry modules, one runner), but the real center of gravity is registry/ at 65 modules and 19.7k LOC, 70% of which is PR/review/mission ops automation rather than scientific memory, with maintainer_review.py (2,543 lines, a 771-line report-composer function, 67 commits since May) as the single hottest coordination bottleneck. The second structural tax is the workflow layer: 16 benchmark workflows are 42-63% line-identical copy-paste clones dispatched by a hand-edited if-chain in runner.py and validated by one global config schema, so each new benchmark costs ~1,000 duplicated lines and three coordinated edits. Layering between registry and engines is bidirectional (including engine execution during config validation), two modules invert the dependency onto scripts/ making the declared installable package fictional, and only the 16 workflow paths are CLI-replayable while 69 scripts drive 55 mostly task-frozen engines directly — the project already pays a documented repackaging cost to make script-born results Gate B-replayable. What works well: cli.py is a clean 439-line, 9-command surface (not a monolith); scientific_memory_integrity.py itself is well-scoped at 483 lines; there are no fully dead modules; test coverage is broad (227 test files); and factories/core.py demonstrates exactly the Protocol-based adapter pattern the workflow layer needs. The biggest single problem is the registry god-package plus its churn-magnet review module; the highest-leverage fix is splitting ops out of registry and templating the workflow layer with registry-dict dispatch.

## Agent task-workflow bottlenecks

The APL task workflow is unusually well-tooled — helpers exist for 4 of 5 PR shapes, a 3,100-LOC deterministic review-check layer, an auto-closeout sweep, and an occupancy/claiming apparatus — but the last mile is structurally defective in two ways. First, the enforcement backbone is opt-in: apl_review_pr.py and the finish gate never run in CI, so of 15 sampled protocol rules only 2 are CI-enforced, 7 are helper-backed-but-voluntary, and 6 are prose-only, which is exactly why the same failure classes (dismissed NEEDS_CHANGES, CI-only failures, stacked-PR losses) keep recurring. Second, the automation that does exist is defeated by defaults: 107/109 active tasks set `closeout: review`, so only 10 of 336 board-sync commits in 30 days auto-closed anything and all 10 current REVIEW_READY tasks are already-merged pure closeout lag waiting on manual maintainer commits. The biggest single problem is this closeout/enforcement gap keeping the maintainer as the manual serializer for every task's tail end. Meanwhile the READY science pool is at 7 vs a minimum of 12 today, and the task_queue_needed warning that should signal this is OR'd from five near-always-true conditions, so it carries almost no information. Token waste concentrates in a ~2,150-line minimum onboarding read chain (≈5,700 lines at full protocol-link closure) repeated per agent session, a 6-required-flag PR helper whose boilerplate was flagged as an incident learning and never fixed, and a git history that is 38% bot noise despite the protocol declaring git log "the task history". What works well: the postmortem-to-guardrail loop has produced real structural fixes (board-sync action ending merge-conflict dances, HARNESS_IGNORE_PATHS, overclaim detectors), the closeout sweep's protected-artifact safety logic is sound, and duplicate-work prevention via the occupancy helper plus onboarding availability filtering appears effective in practice.

## Scientific-integrity gates (Gate A/B, promotion funnel)

The Gate A/B/C architecture is genuinely well designed — verdict vs review-tier separation, first-class negative results, honest same-owner replay annotations — but enforcement consistently lags design by one layer: rules live in Gate B code and protocol prose while Gate A, the creation-time chokepoint, checks almost none of them. ## External-contributor experience

External-contributor experience is the weakest surface of an otherwise disciplined repo. The mechanical rails are genuinely good: the Python 3.9-vs-3.11 trap is handled cleanly (running `python3 -m pytest` under macOS system Python 3.9.6 yields an actionable RuntimeError from physics_lab/_runtime.py telling you exactly how to build a venv, and the mission script itself deliberately runs on old interpreters), the CI fork-guard correctly routes fork PRs to disposable GitHub-hosted runners, and PR helpers mechanically catch branch/title/body mistakes. But the funnel above those rails is broken in three ways. First, the required reading before a first edit is ~3,800 lines / 22,084 words (~30k tokens) across 11 documents encoding ~13 distinct format-rule families and 6 branch shapes, and two of those required documents contain statements that are now false (the protocol still forbids making the repo public; AGENTS.md claims 11 experiments when there are 20). Second, there is no viable first task: the microtask "easy lane" has zero available items (17 completed, 2 retired), no good-first-task label exists anywhere, and every current READY task is campaign-embedded — the mission script's #1 recommendation (TASK-0964) is explicitly sequenced after an unmerged task, another is reserved for the maintainer's own identity lane, and all are advertised with a hardcoded "~5-10 min" estimate that is off by 1-2 orders of magnitude. Third, the fork path — the only path a true outsider has — is never documented (the word "fork" appears in zero contributor docs) and the observed practice is granting outside collaborators write access instead (193 of the last 200 PRs are same-repo; the only 7 fork PRs ever came from one contributor over 3 days and stopped). Realistic clone-to-first-mergeable-PR for a competent outsider is 8-13 hours, of which barely a third is actual science: ~0.5-1h environment, 2-3h required reading, 1-2h task+memo context, 3-5h implementing a medium task, 0.5-1.5h validation/CI-gotcha iteration, 0.5-1h claim+PR packaging. The single biggest problem is the empty on-ramp: a capable stranger arriving today finds nothing they can execute without campaign context or maintainer interaction, told it will take 10 minutes.

## CI/CD and repository safety

Audited all three .github/workflows/*.yml files in full plus the guard code they invoke (scripts/apl_closeout_sweep.py, physics_lab/cli.py sync-active-board, and physics_lab/registry/{closeout_sweep,generated_state,task_views,tasks}.py). Overall the security posture is above-average for a small public research repo: a fork-guard routes untrusted fork PRs to disposable GitHub-hosted runners (ci.yml:96), the sync-active-board GitHub App bypass is gated by a path-allowlist check that runs BEFORE the privileged token is minted (sync-active-board.yml:97-140), the underlying generator code is structurally bounded to docs/task-views/*.md and TASK-*.yaml status flips, and task YAML is parsed with yaml.safe_load (tasks.py:19,35) so there is no deserialization RCE and no pull_request_target/issue_comment trigger and no committed secret. However, this is not a one-finding dimension. The highest residual risk is that same-repo branch PRs (from any write-access or compromised contributor account) execute attacker-authored Python on self-hosted runners with NO explicit permissions: block in ci.yml, meaning the default GITHUB_TOKEN scope is reachable from untrusted code. The board-sync job also runs merged-main code via `pip install -e .` while a contents:write App token that bypasses branch protection is in scope, so a malicious change to the generator itself (once merged) runs with the bypass. All GitHub Actions are pinned to floating major tags rather than commit SHAs, and every Python dependency in pyproject.toml is an unpinned `>=` floor, giving a supply-chain drift path onto the self-hosted fleet. Findings ranked most-severe first below.

### security-cicd-1: Same-repo branch PRs execute untrusted code on self-hosted runners with no explicit permissions: block (default GITHUB_TOKEN scope reachable)

- Severity: high | verification: REAUDIT
- Evidence: ci.yml has NO top-level or job-level `permissions:` block anywhere (confirmed: `grep -n permissions .github/workflows/ci.yml` returns nothing; the only permissions blocks are in sync-active-board.yml:53-56 and nightly-full-repo.yml:18-19). The fork-guard at ci.yml:96 sends fork PRs to ubuntu-latest but keeps SAME-repo PRs on self-hosted: `runs-on: ${{ (github.event.pull_request.head.repo.full_name == github.repository) && fromJSON(vars.APL_PR_RUNNER_LABELS || '["self-hosted","linux","x64"]') || 'ubuntu-latest' }}`. On that self-hosted runner the pull-request job runs attacker-authored code: `pip install -e ".[dev]"` (ci.yml:114, executes setup.py/build hooks from the PR head), `pytest` (ci.yml:141) and `python -m physics_lab.cli validate-repo/run` (ci.yml:122,193). With no permissions block, GITHUB_TOKEN defaults to the repository/org default scope, which is exposed to that untrusted code.
- Impact: Any actor who can push a branch to the repo (every write-access contributor, plus any compromised contributor token or a maintainer's second account) — not just fork authors — gets arbitrary code execution on the self-hosted runner with whatever the default GITHUB_TOKEN scope is. If org/repo default token permissions are read/write (GitHub's legacy default), that token can push, alter releases, or tamper with other workflow artifacts. The fork-guard mitigates the anonymous-internet case but the same-repo branch path is the more likely real-world compromise vector for this project (per the maintainer's own notes, multiple contributor identities and a second maintainer account exist).
- Recommendation (advisory): Add an explicit least-privilege `permissions: { contents: read }` block at the top of ci.yml (jobs can widen individually if needed). Separately, harden the self-hosted runners: ensure they are ephemeral/single-use (fresh VM per job) so a same-repo-PR compromise cannot persist or pivot, and consider requiring an approval gate (environment protection) for first-time or non-maintainer contributors' PRs before self-hosted execution.
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).

### security-cicd-2: Board-sync job runs merged-main code via editable install while a branch-protection-bypassing App token is in scope

- Severity: high | verification: REAUDIT
- Evidence: sync-active-board.yml checks out main (line 68-73), installs the merged tree editable (`pip install -e .`, line 85), then runs merged-tree code: `python scripts/apl_closeout_sweep.py --auto-safe` (line 91) and `python -m physics_lab.cli sync-active-board .` (line 95). It later mints a GitHub App token with `permission-contents: write` (line 145-149) that the maintainer is instructed to grant a branch-protection bypass (header comment lines 39-41), and pushes directly to main with it (line 171-172: `git remote set-url origin https://x-access-token:${BOARD_SYNC_TOKEN}@...`; `git push origin HEAD:main`). The path-allowlist guard (lines 108-122) constrains the git DIFF, but it does not constrain what the generator CODE does at runtime — it runs whatever generated_state.py / closeout_sweep.py / task_views.py contain in the merged tree.
- Impact: The trust boundary of the bypass is 'code already merged to main', not the diff guard. A malicious or buggy change to the generator itself (e.g. an edit to physics_lab/registry/generated_state.py or closeout_sweep.py that passes PR review) would, once merged, run with a token that can push to protected main. The self-imposed diff guard would still have to be defeated, but the generator code runs before/around that guard and could in principle also craft its output to satisfy the allowlist. The compensating control (guard runs before the token is minted at line 142, and yaml.safe_load prevents task-YAML deserialization RCE) makes this hard, not impossible — it is a standing privileged-automation surface.
- Recommendation (advisory): Pin the sync workflow to a known-good generator: either (a) run sync-active-board from a trusted tagged/pinned version of physics_lab rather than the just-merged HEAD, or (b) split the privileged push into a separate minimal step that does NOT `pip install -e .` from the merged tree (install the generator from a pinned wheel/ref). Additionally, scope the App installation to only the paths it needs if GitHub path-restricted app permissions become available, and keep the App's bypass narrowly to this one workflow identity as the header already advises.
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).

### security-cicd-3: GitHub Actions pinned to floating major-version tags instead of commit SHAs

- Severity: medium | verification: REAUDIT
- Evidence: Every `uses:` reference is a mutable tag, none SHA-pinned (grep 'uses:' across all three files): actions/checkout@v5 (ci.yml:24,102,169,212; sync-active-board.yml:69; nightly-full-repo.yml:31), actions/setup-python@v6 (ci.yml:105,172,215; sync-active-board.yml:76; nightly-full-repo.yml:36), and — most critically — actions/create-github-app-token@v3 (sync-active-board.yml:145), the action that handles the private key (secrets.APL_BOARD_SYNC_APP_PRIVATE_KEY) and mints the contents:write bypass token.
- Impact: A tag is mutable: if any of these action repos (or a maintainer's tag) is compromised and the v5/v6/v3 tag is repointed, the malicious action runs in APL's workflows on the next trigger. For create-github-app-token@v3 that means the compromised action executes in the same job that holds the board-sync App private key and produces the branch-protection-bypass token — a direct path to reading the private key or exfiltrating the minted token. The self-hosted runners (ci.yml) further widen the blast radius of a compromised checkout/setup-python action.
- Recommendation (advisory): Pin all actions to full 40-char commit SHAs (e.g. `actions/checkout@<sha> # v5`), prioritizing create-github-app-token given it touches the App private key. Add Dependabot/renovate for the GitHub-actions ecosystem so SHA bumps are proposed as reviewable PRs, and consider an allowlist of permitted actions at the org level.
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).

### security-cicd-4: All Python dependencies floating (>= floors) with no lockfile — supply-chain drift onto self-hosted runners

- Severity: medium | verification: REAUDIT
- Evidence: pyproject.toml declares only lower bounds, no upper caps and no committed lockfile: jsonschema>=4.0, numpy>=1.26, scipy>=1.11, sympy>=1.12, pydantic>=2.0, typer>=0.12, pyyaml>=6.0 (lines 13-19), pytest>=8.0/pytest-cov>=5.0/pytest-xdist>=3.6/ruff>=0.6 (dev, lines 24-28). CI installs these fresh with `pip install --upgrade pip` then `pip install -e ".[dev]"` (ci.yml:113-114, 180-181; sync-active-board.yml:84-85; nightly-full-repo.yml:44-45). `cache: pip` keyed on pyproject.toml (ci.yml:108-109) does not lock transitive versions. Note two deps ARE pinned exactly (rdkit==2025.9.3, thermo==0.6.0, lines 31-32), showing the repo knows how to pin but did not for the core set.
- Impact: A malicious or broken new release of any core/transitive dependency is pulled automatically on the next CI run, executing on the self-hosted fleet (main-matrix, and same-repo PRs) with whatever privileges those runners carry. This is the classic 'CI installs a fresh unpinned dep and it runs your infra' supply-chain exposure; combined with finding #1's missing permissions block it compounds the self-hosted-runner risk.
- Recommendation (advisory): Commit a lockfile (pip-tools requirements.txt with hashes, uv.lock, or equivalent) and have CI install from it with `--require-hashes`. At minimum add upper bounds to the core runtime deps. Keep the good rdkit/thermo exact-pin pattern and extend it.
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).

### security-cicd-5: Board-sync path-allowlist accepts arbitrary content in any tasks/TASK-*.yaml, not just the intended status flip

- Severity: low | verification: REAUDIT
- Evidence: The 'Detect regeneration diff' guard (sync-active-board.yml:108-122) allows a changed path if it matches `docs/task-views/*.md|tasks/TASK-*.yaml` — it validates the PATH, never the CONTENT of the change. The auto-safe closeout that runs first (line 91) only rewrites `status: REVIEW_READY` -> `status: DONE` (closeout_sweep.py:380-383, single-occurrence replace) and the sync only writes docs/task-views/*.md (task_views.py:151-155), so today the writes are code-bounded. But the commit step then does `git add docs/task-views/ tasks/` (line 162) — staging the ENTIRE tasks/ tree — and the guard would pass any change confined to TASK-*.yaml filenames regardless of what fields changed.
- Impact: Defense-in-depth gap rather than an active exploit: the guard's safety currently rests entirely on the generator code being well-behaved, not on the guard itself. If a future change to closeout/sweep logic (or a bug) caused edits to non-status fields of a TASK-*.yaml, or staged an unexpected pre-existing dirty TASK file, the guard would not catch it and the change would be pushed to protected main under the App bypass. Impact is bounded to task metadata (no code paths), hence low.
- Recommendation (advisory): Tighten the guard to assert the SEMANTIC diff, not just the path: e.g. run `git diff` and reject any staged TASK-*.yaml hunk that changes lines other than `status:`, and stage only the specific files the closeout/sync steps reported as changed (returned by apply_auto_safe_closeouts.changed_files / sync_task_views) rather than `git add tasks/` wholesale.
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).

### security-cicd-6: Auto-safe closeout 'protected artifact' guard depends on a live gh PR-files lookup that fails open to empty

- Severity: low | verification: REAUDIT
- Evidence: auto_closeout_blockers (closeout_sweep.py:283-306) blocks auto-closeout if the merged PR touched a PROTECTED_ARTIFACT_PREFIXES path (claims/, results/, prediction_registry/, experiments/, knowledge/ — lines 246-252). But the changed-file list comes from load_pr_changed_files (lines 309-332) which shells out to `gh pr view <n> --json files`; on ANY non-zero return it returns `()` (line 330-331), and auto_safe_closeout_candidates passes `pr_files or ()` (line 352). An empty changed-file set means the `protected` filter (lines 293-297) finds nothing and raises no blocker — the task is treated as auto-safe. The step runs with the default GITHUB_TOKEN (sync-active-board.yml:89).
- Impact: If the gh lookup transiently fails (rate limit, token scope, network), the protected-artifact safety check silently degrades: a task whose PR actually touched claims/ or results/ could be auto-closed and its status flip pushed to main via the App bypass without the intended human-review gate. Low severity because it only flips a task status (no code/artifact content is changed) and requires the gh call to fail at the wrong moment, but it is a fail-open safety control.
- Recommendation (advisory): Make load_pr_changed_files failures fail CLOSED for auto-safe: distinguish 'PR touched no protected files' from 'could not determine PR files' and treat the latter as a blocker (skip auto-closeout, report-only), mirroring how full_repo_signal_status already falls back to report-only on unknown signal (apl_closeout_sweep.py:64-70).
- Verifier notes: Produced by the Opus security re-audit pass (the Fable pass returned only 1 finding for this dimension).
